0.2

Decisions at a glance

Ten decisions shape everything else. Each one has a full record in 5.2.

ADR-001

Rust workspace, ports & adapters

The core depends only on traits. Providers, tools and stores plug in from the outside, so any one can be swapped without touching the rest.

ADR-002

Event-sourced, SQLite as the truth

Every input, output, tool call and decision is an event in one SQLite file inside the project. State is rebuilt by replaying events.

ADR-003

Append-only transcripts

History sent to a model is never edited. That keeps the prompt cache warm and keeps Claude's preserved thinking valid. Compaction starts a new segment instead.

ADR-004

Anchored compaction + recall

Summaries carry descriptive anchors that point into the event log. The model can call recall to get exact details back. This is your idea, made safe for append-only.

ADR-005

SQLite FTS5 first for memory

Full-text search, plus vectors later via sqlite-vec, behind a MemoryStore trait. RushDB and graphify stay optional plug-ins.

ADR-006

Persona = bundle, subagent = persona

A persona bundles prompt, model, tools, skills, MCP servers, hooks, policy and memory scope. A subagent is just a persona started with a fresh context.

ADR-007

Standards over invention

Use AGENTS.md, SKILL.md and MCP exactly as other tools do, so their ecosystems work with yours.

ADR-008

Legitimate auth only

API keys and official sign-in programs. No reuse of Claude subscription logins. A subscription is used only by running the vendor's own CLI as a delegate, where its terms allow.

ADR-009

Extensions run out of process

Hooks are commands, tools can come from MCP servers, and external agents are delegates. A broken extension can't crash the harness.

ADR-010

Linux-first sandbox

bubblewrap with no network by default. Rules decide when to ask, the sandbox decides what is possible. macOS comes later.

Part 1 · Product Requirements Document

What we are building, for whom, and why

This part defines the product from the user's side. It does not prescribe implementation; that is Parts 2 and 3.

1.1

Vision & problem

Vision: one local harness where you define personas (a coder, a researcher, a writer, an ops helper), each with its own model, tools, skills, MCP servers, hooks, rules and memory. The harness runs them on any supported model provider, keeps every detail of every session, and lets long tasks be paused, resumed and recovered without losing context.

Problems with today's harnesses

  • Each one is tied to one vendor's models and login.
  • Claude Code and Codex are coding-first. Hermes is persona-first but not coding-grade on safety.
  • Compaction is one-way. Details lost in a summary are gone, and the model guesses instead.
  • Pause and resume is shallow: you can resume a chat, but not a half-done task after a crash.
  • File inputs beyond text and images are patchy.

What this harness does differently

  • Persona is the unit of configuration Hermes
  • Rules plus hooks plus sandbox, all three Claude Code Codex
  • Restorable context: anchors and recall over a complete event log New
  • Durable tasks with play, pause, resume, crash recovery and fork New
  • Provider-neutral core with capability flags New
1.2

Goals & non-goals

Goals

  • G1 Persona-driven, general-purpose agent: coding, research, writing, ops.
  • G2 Hooks, skills, MCP, subagents and tools as first-class features.
  • G3 Accept text, images, PDFs, office files, audio, video and archives.
  • G4 Durable sessions and tasks with play, pause, resume, cancel, crash recovery and fork.
  • G5 Long sessions without detail loss, through anchored compaction and recall.
  • G6 Multiple providers: Anthropic and OpenAI first, more later.
  • G7 Modular: replace any component without touching the others.
  • G8 A learning project. The code should stay readable, documented and tested.

Non-goals (v1)

  • NG1 No GUI or web app. Terminal, headless and JSON-RPC only.
  • NG2 No hosted or cloud service, and no multi-user server.
  • NG3 No Windows sandbox. Windows can run, but with warnings.
  • NG4 No in-process dynamic plugins (.so/.dll).
  • NG5 No reuse of subscription OAuth tokens outside the vendor's own tools.
  • NG6 No model training or fine-tuning.
  • NG7 No graph database server in v1.

Constraints, assumptions & open questions

Constraints

  • Anthropic's consumer terms forbid using Claude subscription logins in third-party tools, and this is enforced since early 2026.
  • There is no official Anthropic Rust SDK, so the harness calls the HTTP API directly.
  • On Claude Opus 5.5 and newer, thinking can't be turned off, assistant prefill is rejected, forced tool_choice is rejected, and editing history invalidates later thinking blocks.
  • API version 2026-10-21 rejects temperature, top_p and top_k.

Assumptions

  • Single user, single machine.
  • Linux with unprivileged user namespaces, so bubblewrap works.
  • You have API keys for Anthropic and OpenAI.
  • You work about 15–20 hours a week. The plan's estimates assume that.

Open questions

  • Q1: Can your app register for ChatGPT sign-in? Decide in Phase 12.
  • Q2: Do the vendors' terms allow using their CLIs as delegates for your use? Re-check in Phase 12.
  • Q3: Should auto-recall be on by default? Decide from the Phase 14 eval.
  • Q4: Is WASM worth it for in-process extensions? Decide after v1.0.

2.2

Design principles

P1

Depend on traits, not implementations

The runtime crate never imports a provider, store or tool crate. The binary wires everything together.

P2

The event log is the truth

Anything that matters is an event. In-memory state is a cache that can be rebuilt by replay.

P3

Append, never rewrite

Transcripts, the log and transcript-affecting decisions are all append-only. A change is a new event.

P4

Everything speaks events

The core receives Ops and emits Events. UIs and servers only listen and send. Nothing in a library prints.

P5

Capabilities, not provider names

Code asks "does this model support PDF?" rather than "is this Anthropic?".

P6

Out-of-process extension

Hooks, MCP and delegates run as separate processes, with timeouts and isolation.

P7

Safe by default, explicit to loosen

Every loosening (trust, always-allow, full access) is a visible, logged choice.

P8

Standards over invention

Use AGENTS.md, SKILL.md, MCP and JSON Schema as they are.

2.5

Component designs

C1 · Runtime: session actor, turn engine, task manager

Session actor

One tokio task per open session. It owns that session's in-memory state and receives Ops through a bounded channel, so operations never race. It writes events through the EventLog and broadcasts them to subscribers.

Turn engine

The agent loop for one task: ask the context engine for a request, stream from the provider, collect tool calls, run hooks, policy and approval, execute, append results, repeat. It checks for pause, interrupt and budgets at defined safe points.

Task manager

Owns the task state machine (2.8), budgets, child tasks (subagents), the background queue, and recovery after a crash.

C2 · Providers

A Provider turns a neutral ModelRequest into a vendor's wire format and maps the streamed reply back into neutral ProviderEvents. Provider-specific blocks (Claude's signed thinking blocks, OpenAI's encrypted reasoning items) are kept as Opaque content and replayed exactly.

A ProviderRouter resolves "anthropic/claude-opus-5-5" to an adapter and handles fallback chains. A delegate backend is a different trait, AgentBackend, because it runs a whole agent rather than a single model call. To the runtime it looks like a subagent.

C3 · Tools

Every tool, whether built-in, MCP or skill-provided, implements the same Tool trait. Its risk(input) method returns what the call would touch (read, write paths, run a command, network host), and policy decides from that. Tools receive a ToolCtx holding the sandbox handle, blob store, read ledger, cancel token and event sink.

The read ledger records the path, content hash and mtime of every file read in the session. edit_file checks it. The output capper trims large outputs when they are recorded and adds a recall handle. The PTY manager keeps interactive processes alive across turns.

C4 · Policy & sandbox

Decision pipeline for every tool call: PreToolUse hooks → rules (all layers, strictest wins) → defaults by risk class and approval policy → ask the user if needed → run inside the sandbox. A deny from any source wins.

The sandbox wraps process execution (shell, PTY, hook-free tool subprocesses). File tools in the harness process enforce the same writable roots in code. When a sandboxed command fails on a denied path or blocked network, the result is tagged so the model can ask for escalation with a justification.

C5–C9 · Extensions and personas

Hooks

A HookRunner matches events and tool names to configured commands and runs them with JSON stdin, environment variables and a timeout. It turns exit codes and stdout into decisions. Hooks never edit the transcript; they can only add appended context or block.

Skills

The loader scans the skill locations, parses frontmatter and builds an index of names and descriptions, frozen per segment. The skill tool returns a skill's body and file list on demand.

MCP

McpManager starts a persona's servers when a segment starts, lists their tools, wraps each one as a Tool, and freezes the list for that segment. Changes take effect at the next segment.

Personas

The loader resolves inheritance into a ResolvedPersona, the single input that configures a task: prompt parts, model routing, tool and skill filters, MCP set, hooks, policy profile, memory scope and spawn list.

Subagents

spawn_agent asks the task manager to create a child task with a ResolvedPersona, a fresh session segment, a budget, and permissions intersected with the parent's. Approvals bubble up to the user, labelled with the child's name.

Ingest

Detects the type from the file's bytes, stores the original in the blob store, and either produces native content blocks (when the model supports the type) or converts the file. Large files become attachment cards plus paged reads.

2.6

Context engine design

This component is what makes the harness different. It answers your question 2: every detail is kept, compaction is restorable, and the model can ask for exactly what it needs. It is also built for how current models behave, so it never edits history.

Hard rule from the provider

On Claude Opus 5.5 and newer, each thinking block is cryptographically bound to the exact conversation before it. Editing, removing or inserting an earlier turn invalidates every later thinking block, and the API returns a 400 or drops them. Editing earlier turns also throws away the prompt cache. So the engine never edits a sent transcript. Large outputs are trimmed before they are first sent, and compaction starts a new segment instead of rewriting the old one.

Why descriptive anchors

A model can't know what it has forgotten. A bare [[ev:211-560]] gives no hint that the exact error text is behind it. The has: list tells the model what kind of detail each anchor holds, so it knows when to call recall instead of guessing. Auto-recall covers what the model still misses.

1 · PINNED

Always present

Requirements, decisions, constraints and IDs, copied verbatim into every summary.

Model asks

Harness offers

Entities in new input are searched in older segments. The top hits are appended as a system note.

Across sessions

2.11

Concurrency & error handling

Concurrency model

  • tokio multi-thread runtime. One actor per session. Each task runs in its own spawned future, owned by the task manager.
  • Bounded mpsc channels for Ops (capacity 64) and a broadcast channel for Events (1024, lagging subscribers get a resync event).
  • SQLite: one dedicated writer thread receiving batches through a channel, plus a small pool of read connections. Never call rusqlite on async worker threads.
  • Cancellation via tokio_util::sync::CancellationToken trees: session → task → turn → tool. Cancelling a parent cancels its children.
  • Parallel tool calls use a JoinSet limited by a semaphore (default 4). Subagents share a global semaphore (default 3).

Error taxonomy

  • Libraries use thiserror enums. Binaries use anyhow at the edge.
  • Retryable: 429, 5xx, overloaded, network. Backoff with jitter, max 4 tries, honouring retry-after.
  • Model-visible: tool failures become tool_result with is_error: true. They are never dropped.
  • User-visible: auth, config, refusal, budget. Shown as events with a fix hint.
  • Fatal: event log write failure. The task stops immediately (NFR-03).
  • Every error event carries a stable kind string for scripts.

Policy & sandbox spec

rules.toml (user or project)

Evaluation algorithm

  1. Run PreToolUse hooks. Collect any allow, deny or ask decisions.
  2. For shell, parse the command with tree-sitter-bash and split it on &&, ||, ; and |. Each part is evaluated on its own. Subshells, $(…), backticks, eval and writes outside the writable roots force ask.
  3. Match rules from all layers: built-in, user, project (trusted only), persona profile and session approvals.
  4. Combine all decisions: deny > ask > allow.
  5. No match: ReadOnly is allowed. Write inside the workspace follows the approval policy. Exec is allowed when sandboxed and the policy is on-request, otherwise ask. Network and External ask.
  6. With policy never, ask becomes deny (headless), and the model receives the reason.

MCP spec

Lifecycle and naming

  • Persona servers start in parallel when a segment opens, with a 10 s timeout. A failed server produces a warning and its tools are absent.
  • Tools are named mcp__{server}__{tool}, sanitised to [A-Za-z0-9_-], 64 characters max.

Large tool sets without breaking the cache

When MCP schemas exceed 40 tools or 8,000 tokens, don't swap tools in and out mid-segment, because that edits the request prefix. On Anthropic, declare them all with defer_loading: true plus the server-side tool search tool (it appends schemas and keeps the cache). On other providers, expose two fixed meta-tools: mcp_search {query} returns matching schemas as text, and mcp_call {server, tool, arguments} runs one. The tools array stays fixed either way.

Subagent spec

Result returned to the parent

Rules

  • The child gets the persona's system prompt and a fresh segment with only task, context and attachments. It never receives the parent's transcript.
  • Permissions are the intersection of the parent's effective policy and the child persona's policy.
  • The child finishes by calling the return_result tool (strict schema). If it ends without calling it, the harness makes one more request using structured output to extract the result. Forced tool_choice is not available on current Claude models.

3.13

Context engine spec

Invariants (tested)

  1. I1 Within a segment, request n+1 equals request n plus appended messages: the same system, tools and message prefix, byte for byte.
  2. I2 Every ToolCall in the transcript has exactly one ToolResult before the next model call.
  3. I3 Opaque blocks are replayed unchanged, only within the segment that produced them.
  4. I4 Compaction never happens while an assistant tool call is waiting for its result.
  5. I5 Every pinned fact is a verified substring of its source event.
  6. I6 Anchors of a segment cover all of its events, with no overlap.

Budgets and triggers

  • window = the model's context window from its capabilities.
  • compact_at = min(0.70 × window, compact_at_tokens). Default 250k, because cost matters long before a 1M window fills.
  • Check before every model call, using the last usage.input plus the estimated size of appended content. Call count_tokens when within 10% of the threshold.
  • Preferred trigger: at a turn boundary (the last reply ended with end_turn), before appending the next user input.
  • Emergency trigger: mid-task, after a tool round's results are logged. Summarise everything, including those results, then continue with a synthetic user turn: "Continue the task from the summary above."
  • Manual: /compact [focus].

Compaction algorithm

  1. Append CompactionStarted. Run PreCompact hooks to collect extra instructions.
  2. Render segment N as text, with event numbers on every line and tool outputs in their capped form.
  3. Call the compaction model (default: the persona's model at effort medium) with the template below and structured output.
  4. Validate: each pinned[].quote must be an exact substring of event pinned[].seq. Drop and log any that aren't. Anchor ranges must sit inside the segment. Fill gaps with automatic anchors cut at tool-round boundaries, with topic "unlabelled".
  5. Merge pinned facts: keep earlier active facts, add new ones, and deactivate any the model marks superseded (with the superseding event number).
  6. Store anchors and facts, close segment N, open N+1, and write the opener: environment block + summary rendered from the JSON by a fixed template + pinned facts + anchor index.
  7. Append Compacted. Run PostCompact hooks. The next request starts at the new opener.

Auto-recall (P2)

  1. Runs on new user input, not on tool-result turns.
  2. Extracts keys: file paths, identifiers (CamelCase or snake_case, 6+ characters), error codes, quoted strings, issue numbers.
  3. Searches events_fts in earlier segments and memories_fts. Top 5 by bm25, deduplicated against anchors already recalled in this segment.
  4. Keeps hits above a score threshold, at most 2, within 800 tokens.
  5. Appends them as a system note (Anthropic role:"system", clear_at when available) or a <harness-note> block. Never removed later.
  6. Logs Recalled{auto:true}. The eval measures whether auto-recall helps or distracts.

Safe points (where Pause takes effect)

  • Before each model call.
  • After each tool finishes, before the next tool in a batch starts.

Crash recovery algorithm

  1. Find tasks whose state is Running or AwaitingApproval, and set them to Recovering.
  2. Replay the events of the current segment to rebuild the transcript.
  3. For each ToolStarted without ToolFinished: append ToolFinished{ok:false} with the result "The harness stopped while this was running. Outcome unknown. Check the current state before retrying." Never re-run it automatically.
  4. For a ToolCall that never started: re-run it if it is ReadOnly. Otherwise put it back through policy (it may ask again).
  5. For a TurnStarted without AssistantMessage: discard the partial reply. The next resume calls the model again.
  6. Set the state to Paused with reason recovered and tell the user.

Fork

Op::Fork{session, at} creates a new session with parent_id and forked_at_seq. Events up to at are read through the parent (not copied). New events go to the child. If at falls mid-segment, the fork starts a new segment with a compaction of the parent's segment up to at, because the old thinking blocks belong to the parent's conversation.

Undo

Before any write, the tool snapshots each target file (its blob hash, or NULL if it didn't exist). /undo restores every file touched by the last turn and appends an UndoApplied event plus a system note telling the model which files were reverted.

Part 5 · Guardrails

What not to do, and why the decisions were made

Re-read 5.1 before each phase. Most expensive bugs in agent harnesses come from this list.

5.1

What not to do

01
Don't reuse or spoof Claude subscription logins.

It breaks Anthropic's terms, and requests are blocked server-side. Instead: use API keys, the ant OAuth profile billed to the API organisation, or a delegate that runs the official CLI where its terms allow.

02
Don't edit a transcript after sending it.

On Claude Opus 5.5 and newer, it invalidates every later thinking block, and it throws away the prompt cache on every provider. Instead: append notes, cap outputs when recording them, and compact into a new segment.

03
Don't trim old tool outputs later.

That is a history edit. Instead: decide the capped form when the output is first recorded, and keep the full output in the log behind a recall handle.

04
Don't keep recent turns verbatim after a summary ("keep-tail" compaction).

Their thinking blocks were made with the full history present and fail the check. Instead: use simple compaction: summary + anchors + pending input, and nothing else replayed.

05
Don't put volatile data in the system prompt.

A timestamp, git status or token count there changes the prefix on every call. Instead: put it in the segment opener or an appended note.

06
Don't change the tools array mid-segment.

It edits the prefix. Instead: freeze tools per segment. Use deferred loading plus tool search, or the fixed mcp_search/mcp_call meta-tools.

07
Don't send temperature, top_p, top_k, assistant prefill or forced tool_choice to current Claude models.

They return 400 errors. Instead: control behaviour with effort, prompts, strict tools and structured output.

08
Don't store base64 in events, or reference images by changing URLs.

The log grows fast, and the API binds content by its bytes. Instead: use content-addressed blobs, and send base64 or a Files API id.

09
Don't let runtime import an adapter crate.

Once it does, modularity is gone. Instead: wire adapters in the cli crate, and enforce the rule with a dependency test.

10
Don't build in-process dynamic plugins.

Rust has no stable ABI, and a bad plugin crashes everything. Instead: use hooks as commands, MCP servers and delegates, and consider WASM after v1.0.

11
Don't trust command parsing as your only defence.

There is always another way to write a dangerous command. Instead: rules for convenience, the sandbox as the wall.

12
Don't treat tool, web, file or MCP output as instructions.

That is how prompt injection works. Instead: wrap and label it as untrusted, and keep approvals and the sandbox in front of risky actions.

13
Don't re-run a non-read-only tool after a crash.

git push twice, or a payment sent twice, can't be undone. Instead: report "outcome unknown" to the model and let it check.

14
Don't start with RushDB, a graph database or a vector server.

It adds operations work before you know you need it. Instead: SQLite FTS5, then sqlite-vec, all behind MemoryStore. Add adapters when an eval shows the need.

15
Don't build the TUI before the event protocol, or print from libraries.

Printing tangles the UI into the core. Instead: the core emits events and every front-end listens.

16
Don't block the async runtime or use unbounded channels.

Synchronous SQLite calls on worker threads stall streaming, and unbounded queues hide overload. Instead: a dedicated writer thread and bounded channels.

17
Don't hand-roll MCP or SSE parsing.

Edge cases are endless. Instead: rmcp and eventsource-stream.

18
Don't give subagents more power than their parent.

It becomes an escalation path. Instead: intersect permissions, and set depth, budget and parallelism limits.

19
Don't commit state.db or blobs, and don't log secrets.

Session logs eventually capture keys from command output. Instead: auto-gitignore, keyring-only credentials, and a redaction hook.

20
Don't tune the context engine without an eval.

Intuition about what helps the model is often wrong. Instead: build the needle eval in Phase 5 and change one thing at a time.

5.2

Architecture decision records

ADR-001Rust workspace with ports and adaptersaccepted

Context: You need to change components without breaking others. Decision: a ports crate of traits; runtime depends only on ports; adapters are wired in cli. Consequences: some boilerplate and dyn dispatch, but each piece can be replaced and tested alone.

ADR-002Event sourcing on SQLite (WAL) as the single source of truthaccepted

Context: Pause, resume, recovery, recall and fork all need complete, durable history. Decision: every meaningful action is an event in state.db, committed before its side effects. JSONL is export-only. Consequences: one file to back up, transactional durability, and full-text search included. You need a writer thread.

ADR-003Append-only transcripts with segmentsaccepted

Context: Current Claude models bind thinking to the exact prior conversation, and all providers cache by prefix. Decision: never edit sent history. Compaction opens a new segment. Consequences: requires output capping when recording and a careful request layout. Gives maximum cache hits and valid thinking.

ADR-004Anchored simple compaction instead of keep-tail or server-sideaccepted

Context: Summaries lose details. Keep-tail breaks thinking. Server compaction can't hold your anchors. Decision: structured summary + verified pinned quotes + descriptive anchors + a recall tool. Server compaction stays available as an eval baseline. Consequences: one extra model call per compaction. Details become restorable.

ADR-005SQLite FTS5 (then sqlite-vec) for memory; RushDB and graphify optionalaccepted

Context: You asked whether RushDB or graphify improve memory. Decision: graphify solves code-structure exploration, so integrate it as a skill or MCP server. RushDB needs a Neo4j server; add it as a MemoryStore adapter only if you need shared memory across agents or machines. Consequences: zero-ops local memory now, with a clear upgrade path.

ADR-006Persona is a bundle; a subagent is a persona instanceaccepted

Context: Personas and subagents overlap. Decision: one ResolvedPersona configures every task, top-level or child. Consequences: one mechanism, and any persona can be a subagent.

ADR-007Use AGENTS.md, SKILL.md and MCP as they areaccepted

Decision: read the standard formats and locations, including .claude/skills for compatibility. Consequences: existing skills and servers work on day one.

ADR-008Legitimate auth onlyaccepted

Decision: API keys, the Anthropic OAuth profile for API organisations, and official ChatGPT sign-in if your app can register. Delegates are off by default and gated on the vendor's terms. Consequences: subscriptions are usable only through delegates, where their terms allow.

ADR-009Extensions run out of processaccepted

Decision: hooks as commands, MCP for tools, delegates for agents. Revisit WASM after v1.0. Consequences: process start-up costs a few milliseconds, but crashes and hangs stay isolated.

ADR-010Linux-first sandbox via bubblewrapaccepted

Decision: bwrap with no network by default, Landlock as a fallback, macOS seatbelt as P1, and Windows unsandboxed with warnings. Consequences: strong safety on your platform, and portable later.

ADR-011Two edit toolsaccepted

Decision: edit_file (exact replace + read guard) and apply_patch (multi-file). Personas pick which to expose. Claude models do well with string replace and OpenAI models are trained on the patch format. Consequences: slightly more code, better results on both providers.

ADR-012Raw HTTP providersaccepted

Context: there is no official Anthropic Rust SDK. Decision: reqwest + eventsource-stream, with typed request and response structs and replay tests against recorded streams. Consequences: you track API changes yourself. Fixture tests catch regressions.

5.5

Glossary

Anchor
A labelled pointer in a summary to a range of events in the log, with a list of what that range contains.
Append-only
History only grows. Nothing already sent to the model is changed or removed.
Capability
A feature flag describing what a model supports (vision, PDF, caching style…).
Delegate
An external agent CLI (Claude Code, Codex) run as a subagent. Your tools and rules don't apply inside it.
Event
An immutable record of something that happened. The event log is the source of truth.
Opaque block
Provider data (signed thinking, encrypted reasoning) stored and replayed byte for byte.
Persona
A bundle of prompt, model, tools, skills, MCP servers, hooks, policy and memory scope.
Pinned fact
A verbatim quote (a requirement, decision, constraint or id) carried into every summary.
Policy profile
A named pairing of sandbox mode and approval policy.
Preserved thinking
Claude's thinking blocks are valid only in the exact conversation that produced them.
Recall
Fetching exact past content from the log by anchor, event range or search.
Safe point
A moment in the loop where pausing leaves a valid, resumable state.
Segment
The stretch of a session between two compactions. Each segment starts a fresh transcript.
Session / Task / Turn
A conversation / a pausable unit of work within it / one model call.
