01

What is a harness?

Starting point

A language model by itself can only do one thing: take text in and give text out. It cannot open a file, run a test, or remember yesterday. A harness is the program wrapped around the model that gives it those abilities.

The model never touches your computer directly. It only asks; the harness decides and does.

An analogy

The model is a brilliant chef locked in a room with no kitchen. The harness is the kitchen (tools), the recipe card on the wall (instructions), the health inspector (safety rules), the notebook of past orders (memory), and the waiter who carries messages to the customer (the UI).

Why it matters

Put the same model in two different harnesses and you get two different agents. One might be careful and ask a lot. The other might work fast inside a locked box. That difference comes from harness design, and the rest of this guide is about that design.

02

The agent loop: the heart of every harness

Builds on 01 · harness

Under all the features, both Claude Code and Codex run the same simple loop. If you understand this diagram, you understand 80% of any harness.

One message from you can trigger 5, 20 or 100 trips around this loop. Each trip is one model call, often called a "turn" or "step".

The loop in plain code

history = [your_prompt]
while True:
    reply = model(system_prompt, tools, history)
    history.append(reply)
    if reply has no tool calls:
        show(reply.text); break     # Done
    for call in reply.tool_calls:
        if not allowed(call):        # Safety
            result = "denied"
        else:
            result = run(call)       # Run tool
        history.append(result)       # Add result

Four facts that shape everything

The model never runs anything. It writes a structured request ("call read_file with path X"). The harness carries it out.

The model is stateless. Every call re-sends the whole history. That is why context size and cost matter (see 09).

The model decides when to stop, by replying with plain text and no tool calls.

One reply can hold several tool calls. A good harness runs safe ones, such as reads, in parallel.

If you build one

Your first harness can be this loop plus one tool, "run a shell command". That really is an agent. Every feature in Part B is an improvement to one box in this diagram.

What the model actually sees on each call

Builds on 02 · stateless model03 · context builder

Because the model is stateless (fact 2), the harness sends one big package on every call. Here is what is inside, partway through a typical session.

sys
tools

Illustrative proportions. Early in a session the fixed parts dominate. Later the history and tool output take over.

System promptThe harness's built-in "personality" and rules: how to use tools, coding style, safety behaviour, when to stop. Written by Anthropic or OpenAI. It is the biggest single reason the same model acts differently in each harness.

Tool definitionsA JSON schema for every tool: name, description, parameters. More tools means more tokens on every call.

Instruction filesCLAUDE.md or AGENTS.md: your project's rules ("use pnpm", "run make test"). See 08.

Environment factsWorking folder, OS, date, git branch and status. Codex also states the sandbox and approval mode, so the model knows its limits.

ConversationYour messages and the model's earlier replies and tool calls.

Tool resultsFile contents, command output, search hits. This part grows fastest and is what fills the window.

What a tool definition looks like

{
  "name": "read_file",
  "description": "Read a text file. Returns lines
                  with line numbers.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":   { "type": "string" },
      "offset": { "type": "integer" }
    },
    "required": ["path"]
  }
}

What the model sends back

{
  "type": "tool_use",
  "id": "call_01",
  "name": "read_file",
  "input": { "path": "src/auth.ts" }
}

The harness runs it and answers with a tool_result that carries the same id. Anthropic's API calls these tool_use / tool_result. OpenAI's Responses API calls them function_call / function_call_output. The idea is identical.

05

Tools: the model's hands

Builds on 03 · tool registry, executor04 · tool definitions

The first big design choice is whether to give the model many specialised tools or one powerful shell and let it use Unix commands. The two harnesses lean opposite ways.

Claude Code: many dedicated tools
  • Read: files with line numbers, plus images, PDFs and notebooks
  • Write and Edit: create or change files (see 06)
  • Glob finds files by pattern. Grep searches content, built on ripgrep.
  • Bash: run commands, with a background mode for servers and long jobs
  • WebFetch and WebSearch
  • Agent: start a subagent (see 09, 11)
  • TodoWrite, plan mode, AskUserQuestion (see 10)
  • Skill, NotebookEdit, MCP tools, and tool search, which loads rarely used tools only when needed
Codex: a small set, shell first
  • shell / exec_command: run commands. "Unified exec" gives each process a real terminal (PTY), so the model can keep a process alive and type into it later (write_stdin).
  • apply_patch: edit files with a diff (see 06)
  • update_plan: a checklist (see 10)
  • view_image, optional web_search, MCP tools, and in newer versions subagent tools
  • No separate read or search tools. The model runs rg, cat, sed -n and ls in the shell.
Trade-offMany tools (Claude Code)Shell first (Codex)
Safety checksEasy. "Allow every Read, ask for Bash" is a simple rule.Hard to judge a raw command string, so Codex relies on the OS sandbox (07).
Output qualityStructured, truncated sensibly, with line numbers built in.Whatever the command prints. The harness truncates long output.
Prompt sizeMore tool schemas sent on every call. Tool search reduces this.Very small tool list.
FlexibilityBash is still there for anything else.Anything the shell can do, including interactive programs through the PTY.
Use case · "Where is the login token checked?"

Claude Code: Grep(pattern="validateToken") returns 3 files, then Read("src/auth.ts", offset=40, limit=50). Both are read-only, so they can run without asking.

Codex: shell: rg -n validateToken, then shell: sed -n '40,90p' src/auth.ts. They run inside the sandbox, which allows reading, so no prompt appears.

If you build one

Start with run_shell only. Then add read_file and edit_file. You will notice that dedicated tools make the model more reliable and make permission rules much easier to write.

06

Editing files: find-and-replace vs patches

Builds on 05 · tools

Changing code is the most important thing a coding agent does. A bad edit format means broken files. The two harnesses use very different formats.

Claude Code: exact string replace
Edit(
  file_path  = "src/auth.ts",
  old_string = "if (token.exp < now)",
  new_string = "if (token.exp <= now)"
)
  • old_string must appear exactly once, or the edit fails. A replace_all flag is available.
  • Read-before-edit guard: the harness refuses an Edit on a file the model has not Read in this session, and also when the file changed on disk since it was read. This stops edits based on a guess.
  • Write creates a new file or replaces a whole file.
  • One file per call. Several Edit calls can be sent at once.
Codex: apply_patch diffs
*** Begin Patch
*** Update File: src/auth.ts
@@ function validateToken
-  if (token.exp < now) return false;
+  if (token.exp <= now) return false;
*** Add File: src/auth.test.ts
+import { validateToken } from "./auth";
*** End Patch
  • A custom diff format the OpenAI models are trained on.
  • One call can update, add, delete and move several files.
  • The @@ line and the context lines locate the change, so line numbers are not needed. The harness matches the context loosely to allow for whitespace drift.
  • The patch is checked against the sandbox's writable paths before it is applied.
Use case · rename getUser to fetchUser in 3 files

Codex: one apply_patch call with three *** Update File sections. It is one atomic step that you review once.

Claude Code: Read each file, then three Edit calls, which can go in parallel. Each edit is small and checked, and you can approve them one at a time.

If you build one

Implement string replace first. It takes about 20 lines and fails loudly, which is good. Add the "must have read the file, and it hasn't changed since" check: store a hash or mtime when the file is read. A patch parser is a great second project. Codex's apply-patch crate is open source and readable.

The model might run rm -rf, read your .env, or send data to the internet, whether by mistake or because a web page tricked it (prompt injection). A harness has two kinds of defence. Claude Code leads with the first, Codex with the second, and both now offer both.

  • Exec-policy rules: Starlark .rules files in ~/.codex/rules/ mark command prefixes as allow, prompt or forbidden. When rules overlap, the strictest one wins.
  • Newer versions add smart approvals, where a guardian subagent reviews risky requests, and permission profiles that split filesystem and network policy.

Use case · the test suite tries to download a package

Codex (Auto): npm test starts without a prompt, because running inside the project is allowed. The download fails: the kernel has blocked the network. The model sees the error and asks to re-run with escalated permissions. You approve once.

Claude Code (default): before running, it asks "Allow Bash(npm test)?". You pick "Yes, don't ask again" and it becomes a rule. The download works unless you turned on the Bash sandbox.

The core lesson

Rules are easy to understand, but they are only as good as their pattern matching: Bash(curl:*) does not catch python -c "urllib...". A sandbox is very strong, but it is per-OS and harder to build. Serious harnesses use both: rules for convenience, a sandbox as the last wall.

If you build one

You are on Linux, so you can build Gate 2 with one command. bwrap --ro-bind / / --bind "$PWD" "$PWD" --tmpfs /tmp --dev /dev --proc /proc --unshare-net --die-with-parent sh -c "$CMD" gives you a read-only system, a writable project and no network. That is roughly Codex's workspace-write mode.

08

Instructions & memory: CLAUDE.md vs AGENTS.md

Builds on 04 · instruction files

Every project has rules the model can't guess: "use pnpm", "tests live in /spec", "never touch legacy/". Both harnesses read a Markdown file and inject it into every request. They differ in where they look and in what else they remember.

Claude Code: CLAUDE.md + memory
/etc or managed policy CLAUDE.md org-wide ~/.claude/CLAUDE.md you, all projects repo/CLAUDE.md team, committed repo/.claude/CLAUDE.md also team repo/src/api/CLAUDE.md loaded when Claude works in that folder
  • @path/to/file imports another file into it.
  • /init writes a first CLAUDE.md by scanning the repo. /memory opens it for editing.
  • Auto memory: Claude can save its own notes, such as your preferences or project facts, to a memory folder. An index of them loads each session.
Codex: AGENTS.md (open standard)
~/.codex/AGENTS.md you, all projects repo/AGENTS.md team, committed repo/pkg/AGENTS.md each folder from root repo/pkg/web/AGENTS.md down to where you are any level: AGENTS.override.md replaces, not adds
  • AGENTS.md is a cross-tool convention that many coding agents read, so one file works across tools.
  • Files are concatenated from the root down, so deeper files can refine earlier ones. A byte cap (project_doc_max_bytes) keeps it from growing out of control.
  • /init writes a first AGENTS.md.
Use case · a monorepo with a Python backend and a React frontend

The root file says "Run make check before finishing." backend/ has its own file ("use uv, type-hint everything") and frontend/ another ("use pnpm, no default exports"). When the agent works in frontend/, both harnesses combine the root rules with the frontend rules. Claude Code loads the subfolder file when it touches files there. Codex walks the path from the root to the working folder when the session starts.

If you build one

Read AGENTS.md, since it is the shared convention. Walk from the git root to the working folder, concatenate the files, and put the result early in the prompt, after the system prompt. A stable position keeps prompt caching working (09).

Context management: fitting a long job in a fixed window

Builds on 02 · stateless04 · request package

Every call re-sends everything (fact 2), and tool results pile up fast. Without care, a long session gets slow, expensive, and eventually overflows the model's context window. These are the five standard techniques.

Compaction asks the model to summarise the old history ("goal, decisions, files changed, next steps"), then replaces the history with that summary and the most recent messages.

1

Prompt caching

If the start of the request is identical to the last call, the provider reuses its work, which is cheaper and faster. That is why the system prompt and tools stay fixed and new content goes at the end.

2

Compaction

Summarise old history when the window gets full. It can run automatically, or by hand with /compact in both tools.

3

Truncation

Cut huge tool outputs, such as a 50,000-line log, keeping the head and tail. Both harnesses cap output size.

4

Subagents

Hand a messy search to a child agent with its own empty window. Only its short report comes back to the parent.

5

Lazy loading

Show only a one-line description of each skill or rarely used tool, and load the full content when it is actually needed.

+

Show usage

Claude Code's /context draws a breakdown of the window. Codex's /status shows token usage.

Claude Code
  • Auto-compact near the limit. /compact focus on the auth work lets you steer the summary.
  • Explicit prompt-cache breakpoints in the Messages API.
  • Subagents (Agent tool) are central: the built-in Explore and Plan agents keep file dumps out of the main window.
  • Skills and deferred tools load lazily through tool search.
Codex
  • Auto-compaction through the Responses API, which can return an encrypted, compressed summary item.
  • Reasoning items (the model's hidden thinking) are carried between turns in encrypted form, so the model doesn't "forget why" mid-task.
  • Automatic prefix caching on OpenAI's side.
  • Shell output is truncated before it enters history. Subagents were added in 2026.
Use case · "Find every place we call the old payments API"

Done in the main window, this means 40 grep and read results, about 60k tokens of noise. Done with a subagent, the child does all of that in its own window and returns: "11 call sites, listed with file:line, 3 use the deprecated retry flag." The parent's window grows by about 300 tokens.

If you build one

Count tokens after every call. At about 80% of the window, run a "summarise this session" call and rebuild the history as [system, summary, last 4 messages]. Then add output truncation. These two together solve most context problems.

10

Planning: thinking before doing

Builds on 05 · tools09 · long sessions

On big tasks, models drift: they forget step 6 of 9, or start editing before they understand the code. Harnesses fight this by giving the model a checklist tool, and sometimes a separate planning phase.

Claude Code
  • TodoWrite: the model keeps a live checklist (pending, in progress, done), drawn in the terminal.
  • Plan mode: a read-only phase. The model may only explore, then writes a plan, and you approve it before any file changes. It is a mode of the harness, so the tools are actually locked rather than the model just being asked to hold back.
  • AskUserQuestion: the model can pause and give you multiple-choice options when a decision is really yours.
Codex
  • update_plan: the model posts a checklist of steps with statuses, drawn in the TUI.
  • The read-only sandbox doubles as an "explore only" mode: the model physically can't edit.
  • Newer versions add a plan-style collaboration mode and a persistent goal mode for long-running objectives. Check your version.
Use case · "Migrate the test suite from Jest to Vitest"

Plan first: the agent reads the config, counts 140 test files, and finds 6 that use Jest-only mocks. It proposes 7 steps. You notice it wants to migrate snapshot files too and say "skip snapshots". Then it executes, ticking the checklist as it goes, and you can see it is on step 5 of 7 at a glance.

If you build one

A todo tool is about 15 lines: the model sends the full list each time and you re-render it. It is surprisingly effective. A real plan mode means hiding the write tools from the tool list until the user approves.

Hook example: format every edited file

.claude/settings.json
{ "hooks": { "PostToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{ "type": "command",
    "command": "jq -r '.tool_input.file_path'
                | xargs npx prettier --write" }]
}]}}

The model never needs to remember to format. The harness guarantees it. A PreToolUse hook that exits with code 2 blocks the call. Use it for "never edit files in migrations/".

Skill example: release notes

skills/release-notes/SKILL.md
---
name: release-notes
description: Write release notes from
  git history. Use when asked for a
  changelog or release notes.
---
1. Run `git log --oneline v1.4..HEAD`
2. Group by feat / fix / chore
3. Follow ./template.md

Only the two-line description sits in the prompt. When you ask for a changelog, the model loads the full file. The same format works in both harnesses.

If you build one

Hooks are the cheapest powerful feature. At each point in your loop (before tool, after tool, on stop), run any configured command with a JSON payload on stdin, and treat a non-zero exit as "block, and send stderr back to the model".

12

Sessions, resume and undo

Builds on 04 · history06 · edits

The history list from 02 is just data. Save it to disk and you get resume. Snapshot files before each edit and you get undo.

Claude Code
  • Transcripts saved as JSONL, one event per line, under ~/.claude/projects/<project>/.
  • claude --continue resumes the last session. --resume lets you pick one.
  • Checkpoints: file state is captured before each edit. Press Esc Esc or run /rewind to roll back the code, the conversation, or both. Changes made through Bash commands, such as rm, are not tracked.
Codex
  • "Rollout" files saved as JSONL under ~/.codex/sessions/YYYY/MM/DD/.
  • codex resume opens a picker, codex resume --last continues the most recent, and sessions can be forked.
  • Leans on git: /diff shows everything changed. Versions have offered /undo backed by hidden git snapshots ("ghost commits").
Use case · "That refactor broke everything, go back"

Ten steps ago the agent started a refactor you don't like. In Claude Code you rewind to the checkpoint before it and give a different instruction, and the files and conversation both return. In Codex you inspect /diff, then undo or use git restore. Because the sandbox kept all writes inside the repo, git can see every change.

If you build one

Append every message to a .jsonl file as it happens, not at the end, so a crash loses nothing. For undo, copy each file's old contents before every edit into a per-session folder.

13

Front-ends & automation: one core, many faces

Builds on 03 · front-ends12 · sessions

The best harness design separates the engine (loop, tools, safety) from the face (terminal UI, IDE panel, script). Then the same engine powers everything.

Claude Code
  • claude -p "…": headless, one-shot. --output-format stream-json streams every event for scripts.
  • Agent SDK (TypeScript and Python): the same harness as a library, with its tools, permissions, hooks and subagents. Build your own agent on top of it.
  • IDE extensions, a desktop app, web sessions, GitHub Actions, and background and remote sessions.
Codex
  • codex exec "…": non-interactive. --json emits events, and --output-schema forces the final answer to match a JSON schema.
  • Internal protocol: the core takes a queue of submissions (user input, approval decisions, interrupts) and emits a queue of events (message deltas, "command started", "approval needed", "turn complete").
  • app-server: that protocol as JSON-RPC over stdio. It powers the IDE extension and desktop app. There is also codex mcp-server, a TypeScript SDK, Codex Cloud tasks, and @codex reviews on GitHub.
Use case · a nightly CI job that fixes lint errors

Codex: codex exec --sandbox workspace-write "fix all eslint errors" with --output-schema returning {"fixed": n, "remaining": [...]}, which the CI script reads to decide whether to open a PR.
Claude Code: claude -p "fix all eslint errors" --allowedTools "Edit,Bash(npx eslint:*)" --output-format json, or the GitHub Action, which opens the PR for you.

If you build one

From day one, make your loop emit events (message, tool_start, tool_end, approval_needed) instead of printing directly. Your terminal UI just listens to events. Adding a web UI or headless mode later then becomes easy. Codex's codex-rs/protocol crate is a great reference.

Your first loop (Stage 1)

Builds on 020718 · stage 1

This is the whole agent loop from 02, with Gate 1 (asking you) and a place to add Gate 2 (sandbox). call_model wraps whichever model API you use. The message shapes below follow Anthropic's Messages API. With OpenAI's Responses API the same ideas are named function_call / function_call_output.

mini_harness.py
import subprocess

SYSTEM = "You are a coding agent in the user's project. Use run_shell to inspect and change files. Be concise. When done, reply with a short summary and no tool calls."

TOOLS = [{
    "name": "run_shell",
    "description": "Run a shell command in the project folder. Returns stdout and stderr.",
    "input_schema": {"type": "object",
                     "properties": {"command": {"type": "string"}},
                     "required": ["command"]},
}]

def run_shell(command):
    # Gate 1: ask the human (Claude Code style)
    if input(f"\nRun `{command}`? [y/N] ").strip().lower() != "y":
        return "The user denied this command."
    # Gate 2 (stage 3): wrap in bwrap for a Codex-style sandbox
    p = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=120)
    out = p.stdout + p.stderr + f"\n[exit code {p.returncode}]"
    return out[-10_000:]          # truncate: protect the context window (09)

def agent(user_prompt):
    messages = [{"role": "user", "content": user_prompt}]
    while True:                                            # the agent loop (02)
        reply = call_model(system=SYSTEM, tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": reply.content})

        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:                                         # no tool calls = done
            return "".join(b.text for b in reply.content if b.type == "text")

        results = []
        for c in calls:
            print(f"→ {c.name}: {c.input}")
            results.append({"type": "tool_result", "tool_use_id": c.id,
                            "content": run_shell(**c.input)})
        messages.append({"role": "user", "content": results})   # feed results back

if __name__ == "__main__":
    print(agent(input("What should I do? ")))
